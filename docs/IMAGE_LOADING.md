# 대용량 폴더 이미지 로딩 설계와 검증

작성일: 2026-09-09

30~100 MB 사진 300장이 있는 폴더에서 몽땅보기와 4·5·10장 보기를 안정적으로 사용하면서 다른 앱에 자원 여유를 남기는 것이 이번 개선의 목표다. 주요 사용 환경은 메모리 16 GiB, 내부 SSD 256 GB와 외장 SSD·SD 카드다. 기본값은 **쾌적**이며, 정밀 이미지·Quick Look·이미지 정보 읽기가 하나의 실행 예산을 공유한다. 화면에 필요한 크기로 먼저 읽고, 실제로 보이는 요청부터 처리하며, 지나간 화면의 작업과 이미지 참조를 빨리 정리한다. 이미지 원본이나 내보내기 해상도는 유지한다.

최우선·쾌적·일반·느림은 고정된 CPU 점유율이나 속도를 보장하는 옵션이 아니라 정상 상태의 상한이다. 모든 모드가 시스템 부하·메모리 압박·발열·저전력·앱 활성 상태와 저장장치에 따라 더 낮아진다. 최우선에서도 보호 조건을 해제하지 않는다.

## 파일 용량과 메모리 계산

30~100 MB 파일 300장은 디스크에서 9~30 GB를 차지한다. 하지만 압축 파일의 바이트 수만으로 디코딩 메모리를 계산할 수는 없다. 같은 파일 용량이어도 해상도, 코덱, 비트 깊이, 알파 채널, HDR 여부에 따라 결과가 다르다. Apple 역시 파일 데이터 버퍼와 디코딩된 픽셀 버퍼를 구분하며, 원본을 먼저 펼치는 경로의 비용은 뷰 크기보다 원본 픽셀 수에 좌우된다고 설명한다. [Apple, Image and Graphics Best Practices](https://devstreaming-cdn.apple.com/videos/wwdc/2018/219mybpx95zm9x/219/219_image_and_graphics_best_practices.pdf)

아래 수치는 행 정렬, 임시 디코더 공간, GPU 텍스처와 레이어 비용을 제외한 비트맵 계산이다. SDR RGBA8은 픽셀당 4바이트, 현재 정밀 HDR 출력 RGBA half float는 픽셀당 8바이트로 계산했다. MB·GB는 10진수, MiB·GiB는 2진수 단위다.

| 이미지 | SDR 1장 | HDR 1장 | 예시 합계 |
|---|---:|---:|---:|
| 8,000×6,000, 48 MP 원본 | 192 MB | 384 MB | 원본 300장 SDR 57.6 GB |
| 10,000×10,000, 100 MP 원본 | 400 MB | 800 MB | 원본 300장 SDR 120 GB |
| 최대 512×512 썸네일 | 1 MiB 이하 | 2 MiB 이하 | 화면의 40장 SDR 40 MiB 이하 |
| 최대 1,536×1,536 타일 | 9 MiB 이하 | 18 MiB 이하 | 10장 SDR 90 MiB, HDR 180 MiB 이하 |

썸네일·타일 수치는 정사각형을 가정한 상한이라 가로·세로 사진에서는 더 작다. 몽땅보기의 목록 모델은 300개 파일의 주소와 가벼운 파일 메타데이터를 보관하고, 보이는 셀의 미리보기만 요청한다. 300장 원본을 동시에 펼쳐 보관하지 않는다.

앱 자체의 영구 이미지 디스크 캐시를 새로 만들거나 원본 9~30 GB를 내부 SSD에 복제하지 않는다. 앱이 직접 관리하는 이미지 캐시는 메모리에만 존재한다. macOS Quick Look과 운영체제 파일 캐시는 별도로 존재하며, 그 저장 공간과 정리 시점은 OS가 관리한다.

## Apple 엔진을 유지한 이유

일반 이미지의 축소 읽기는 ImageIO를 유지했다. 소스 생성 시 원본 디코딩 캐시를 끄고, `CGImageSourceCreateThumbnailAtIndex`에 화면용 픽셀 상한과 방향 보정을 지정한다. `kCGImageSourceShouldCacheImmediately`를 사용하면 이미지 생성 과정에서 디코딩하여 나중에 화면을 그릴 때 큰 작업이 시작되는 것을 줄일 수 있다. 현재 소스 생성·축소 디코딩 옵션은 Apple이 제시하는 방식에 기반한다. [Apple ImageIO 즉시 디코딩 옵션](https://developer.apple.com/documentation/imageio/kcgimagesourceshouldcacheimmediately)

몽땅보기와 빠른 첫 화면에는 macOS Quick Look을 사용한다. 이미 만들어진 시스템 미리보기를 활용할 수 있고, RAW 등 시스템이 처리하는 파일 형식도 지원할 수 있다. 실제 캐시 적중 여부와 처리 시간은 OS와 파일 형식에 달려 있다. Quick Look의 요청 취소 API를 앱의 작업 취소와 연결했다. [Apple Quick Look 썸네일 생성과 취소](https://developer.apple.com/documentation/quicklookthumbnailing/creating-quick-look-thumbnails-to-preview-files-in-your-app)

대안인 libvips는 요청된 영역을 중심으로 연산하고 중간 픽셀을 적게 보관하는 구조가 강점이다. 특히 초대형 이미지와 타일 처리에는 검토할 가치가 있다. 그러나 현재 앱의 Apple RAW 처리, HDR gain map, 색상 관리와 Quick Look을 대체했을 때 전체 경험이 더 빨라진다는 측정 근거는 없다. 따라서 이번에는 새 코덱 묶음을 추가하기보다 현재 엔진의 중복 작업과 대기열을 개선했다. [libvips 처리 구조](https://www.libvips.org/API/8.17/how-it-works.html)

## 요청 대기열과 취소

`ImageWorkScheduler`는 같은 파일 버전·프레임·크기·보정·HDR 설정의 요청을 하나의 작업으로 합친다. 이미 진행 중인 선읽기를 화면이 요청하면 해당 작업을 공유하고, 아직 대기 중이면 표시 우선순위로 올린다. 대기 중인 작업은 화면 요청을 선읽기보다 먼저 시작한다. 이미 실행 중인 동기 디코더를 강제로 중단하거나 선점한다는 뜻은 아니다.

`ImageResourceGovernor`는 `ImagePipeline`의 정밀 디코딩·이미지 정보 읽기와 `ThumbnailPipeline`의 Quick Look 표시·선읽기를 **하나의 대기열과 동시 실행 예산**으로 묶는다. 이전 구현의 정밀 최대 4개와 Quick Look 최대 3개라는 독립 상한을 합산하지 않는다. 16 GiB 이상·8코어 Apple Silicon의 정상 내부 SSD에서는 기본 쾌적 모드가 이 경로들을 합쳐 최대 2개까지 시작한다. 캐시에 이미 있는 결과를 돌려주는 데는 새 디코딩 슬롯이 필요하지 않다.

RAW, TIFF, EXR/HDR, 자체 코덱과 원본 해상도 내보내기는 큰 작업용 직렬 디코더를 사용한다. JPEG·HEIC 등 일반 컨테이너에서도 HDR gain map이나 높은 비트 깊이의 HDR 후보가 발견되면 같은 직렬 경로로 보낸다. 이 작업도 공유 예산에 포함된다. 앱이 제한하는 Quick Look 동시성은 앱에서 제출한 요청이며, OS 서비스 내부의 코덱 작업 공간이나 다른 앱의 요청까지 통제하는 것은 아니다.

취소는 요청자별로 관리한다. 같은 사진을 두 셀이 기다릴 때 한 셀이 사라져도 나머지 셀의 작업은 계속한다. 마지막 요청자가 사라지면 대기 중인 작업을 제거하고, 실행 중인 작업에는 취소를 전달한다. Quick Look에는 네이티브 `cancel`을 호출한다. 완료 콜백과 취소가 동시에 발생해도 continuation은 정확히 한 번만 끝낸다.

ImageIO 같은 동기 네이티브 디코더는 호출 중간의 즉시 종료를 보장하지 않는다. 따라서 취소 요청을 보냈다는 이유만으로 실행 슬롯을 새 작업에 재사용하지 않는다. 실제 디코더가 반환할 때 슬롯을 해제하여 빠르게 페이지를 넘겨도 디코더가 제한 없이 늘어나지 않게 했다.

## 모드와 자동 조절

아래는 16 GiB 이상·8코어 Apple Silicon, 내부 SSD, 전경·정상 상태의 상한이다. 코어와 메모리가 적은 기기에서는 더 낮아진다. 설정을 바꾸면 새로 시작할 작업과 대기열, 캐시 예산에 반영한다. 이미 실행 중인 동기 코덱을 강제 종료하거나 실행 중간에 우선순위를 바꾸는 기능은 아니다.

| 모드 | 공유 동시 실행 최대 | 이웃 선읽기 최대 / 시작 대기 | 표시 작업 우선순위 | 작업 사이 최소 대기 |
|---|---:|---|---|---:|
| 최우선 | 4개 | 4장 / 150ms | userInitiated | 없음 |
| 쾌적, 기본값 | 2개 | 2장 / 350ms | utility | 없음 |
| 일반 | 1개 | 1장 / 650ms | utility | 25ms |
| 느림 | 1개 | 없음 | background | 100ms |

선읽기 작업은 항상 background 우선순위를 사용한다. QoS는 macOS가 CPU·효율 코어·I/O를 배치하는 데 사용하는 힌트이며 CPU 코어를 예약하거나 다른 앱보다 무조건 먼저 실행하는 명령이 아니다. [Apple QoS 설명](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/PrioritizeWorkWithQoS.html)

`ImageSystemResourceMonitor`는 utility 큐에서 2초 간격, 400ms 타이머 여유를 두고 공개 `host_statistics` CPU 카운터 차이를 읽는다. 이 수치는 우리 앱을 포함한 전체 CPU 사용량이며 다른 앱의 이름이나 개별 프로세스 목록을 수집하지 않는다. 첫 표본은 비교 기준만 만들므로 CPU 값이 아직 없고, 다음 표본부터 판단한다.

- CPU가 65% 이상이면 선읽기를 멈추고 최대 2개로 낮추며 최우선의 표시 작업도 utility로 내린다.
- 80% 이상이 2회 연속 확인되면 약 4초 만에 최대 1개로 낮춘다. 이 상태는 60% 이하가 3회 연속 확인된 뒤, 약 6초에 걸쳐 해제한다. 짧은 급증과 회복마다 설정이 흔들리는 것을 줄이기 위한 지연이다.
- 앱이 비활성화되거나 저전력 모드, 심한 발열, 메모리 경고·심각 상태가 되면 최대 1개·선읽기 없음으로 바꾸고 작업 사이에 최소 60ms를 둔다. 앱 비활성 시에는 background 우선순위와 평소의 1/4 캐시 예산을 적용한다.
- 가벼운 발열은 최대 2개·선읽기 최대 1장, 선읽기 대기 최소 600ms로 제한한다. 심각한 발열에서는 background와 작업 사이 최소 150ms를 적용한다.

메모리 압박은 Dispatch memory-pressure source, 발열·저전력·앱 활성 상태는 시스템 알림으로 받는다. 타이머와 알림 핸들러는 모니터를 계속 붙잡지 않으며 종료할 때 취소·해제한다. 조건이 회복되면 현재 모드와 저장장치가 허용하는 상한으로 돌아간다. [Apple 메모리 압박 감지](https://developer.apple.com/documentation/dispatch/dispatchsourcememorypressure)

## 내부 SSD, 외장 SSD와 SD 카드

`ImageStorageClassifier`는 선택한 파일이 있는 볼륨의 Foundation 속성과 Disk Arbitration·IOKit의 공개 장치 속성만 읽는다. 사진 내용을 시험 삼아 읽거나 전체 디스크를 훑어 속도를 측정하지 않는다. 분류 결과는 최대 32개 볼륨을 30초간 메모리에 보관한다.

| 저장장치 분류 | 공유 동시 실행 상한 | 이웃 선읽기 |
|---|---:|---|
| 확인된 내부 SSD | 선택 모드의 상한 | 선택 모드의 상한 |
| 확인된 외장 SSD | 최대 2개 | 최대 1장, 최소 600ms 후 |
| SD·이동식 매체 | 1개 | 없음 |
| 네트워크·분류 불명 | 1개 | 없음 |

SD 카드도 기술적으로 solid-state이므로 그 속성만으로 외장 SSD로 판단하지 않는다. 이동식 여부와 Secure Digital 프로토콜이 우선한다. 파티션 속성이 빠져 있거나 부정확할 수 있어 연결된 전체 디스크의 속성도 확인하고, USB 브리지의 불완전한 속성 사전은 해당 장치의 부모 연결만 제한된 깊이로 따라가 확인한다. 전체 디스크의 이동식 정보나 SD 프로토콜을 상위 USB 속성으로 덮어쓰지 않는다. 확인하지 못한 외장 장치는 분류 불명으로 남겨 보수적으로 처리한다. 실제 SD 카드와 모든 USB 카드 리더의 하드웨어 조합을 검증했다는 의미는 아니다.

SD·네트워크·분류 불명에서는 작업 사이 최소 40ms를 둔다. 느림·발열·다른 보호 조건이 더 긴 대기를 요구하면 큰 값을 쓴다. 여러 볼륨에서 선택한 파일이 섞이면 현재 대기 중인 요청 중 가장 보수적인 저장장치의 동시성 상한을 공유 대기열에 적용한다. 외장 SSD로 확인되어도 케이블·브리지·실제 읽기 속도를 보장하지 않으므로 시스템 부하에 따른 추가 제한은 유지한다. [Apple 볼륨 속성](https://developer.apple.com/documentation/foundation/urlresourcevalues/volumeisinternal), [Apple Disk Arbitration 장치 정보](https://developer.apple.com/library/archive/documentation/DriversKernelHardware/Conceptual/DiskArbitrationProgGuide/ManipulatingDisks/ManipulatingDisks.html), [Apple solid-state 속성](https://developer.apple.com/documentation/driverkit/kiopropertymediumtypesolidstatekey)

## Apple Silicon 최적화

현재 Mac은 Apple M3, 메모리 24 GiB, 성능 코어 4개와 효율 코어 4개다. **아래 표는 공유 자원 조절을 도입하기 전 엔진의 동시 디코더 비교 기록이며, 새 기본값인 쾌적 모드의 벤치마크가 아니다.** 당시 동일한 약 98.6 MB 합성 JPEG 10장을 1,280픽셀로 읽으며 2·3·4개 동시 디코더를 비교했다. 순서를 바꾸어 각각 세 번 측정한 중앙값은 아래와 같다. 매번 새 파이프라인을 만들었으며 운영체제 파일 캐시는 따뜻한 조건이다.

| 동시 디코더 | 10장 로딩 중앙값 |
|---|---:|
| 2개 | 2.609초 |
| 3개 | 2.098초 |
| 4개 | 1.614초 |

이 기록은 최우선 모드의 정상 상한을 정하는 참고 자료로 유지한다. 최우선은 활성 코어 수의 절반, 메모리 예산, 최대 4개 중 작은 값을 사용한다. 메모리 8 GiB 미만은 1개, 8~16 GiB 미만은 최대 2개, 16 GiB 이상은 최대 4개이며 Intel은 최대 2개다. 쾌적은 활성 코어 수의 1/4, 메모리 예산, 최대 2개 중 작은 값을 사용하고 Intel은 1개다. 현재 M3·24 GiB에서도 기본값은 공유 최대 2개다. 이는 Apple의 권장 상수가 아닌 앱 정책이며 모든 형식·기기에서 4개가 최적이라는 의미는 아니다.

표시 작업의 우선순위는 모드와 시스템 상태에 따라 결정하고, 실제 성능·효율 코어 배치는 운영체제에 맡긴다. 성능 코어를 앱에서 강제로 고정하지 않는다. [Apple CPU 스케줄링 설명](https://developer.apple.com/videos/play/tech-talks/110147/)

색 보정과 HDR의 `CIContext(options:)`는 이미 기본 Metal 장치를 사용한다. GPU를 명시적으로 지정하는 초기화로 바꾸는 것 자체를 새 가속 기능으로 취급하지 않았다. 컨텍스트는 필요한 순간에만 생성하고 계속 재사용하며, 일반 SDR에서는 GPU용 중간 이미지 생성을 줄였다. [Apple Core Image Metal 컨텍스트](https://developer.apple.com/documentation/coreimage/cicontext/init%28mtldevice%3Aoptions%3A%29-26usb), [Apple CIContext](https://developer.apple.com/documentation/coreimage/cicontext)

Apple Silicon의 통합 메모리에서는 CPU·GPU가 메모리를 공유하므로 작업 수뿐 아니라 중간 복사와 출력 픽셀 수를 줄이는 것도 중요하다. RAW·HDR의 큰 작업 공간은 계속 직렬화하고 메모리 압박 시 처리량을 낮춘다. [Apple Metal과 통합 메모리](https://developer.apple.com/videos/play/tech-talks/10580/)

출력 앱은 arm64와 x86_64를 함께 포함하는 Universal 2 번들이다. Apple Silicon에서는 arm64 코드로 실행한다. Neural Engine 사용이나 모든 사진의 전용 하드웨어 디코딩을 보장하는 구현은 아니다. 현재 SDK에 없는 베타 가속 옵션이나 비공개 문자열 키를 추가하지 않았다.

## 메모리 예산

디코딩 결과 캐시는 사용 바이트를 직접 추적하는 LRU로 바꿨다. 비용은 `bytesPerRow × height`로 계산하며, 캐시보다 큰 한 장은 표시만 하고 캐시에 넣지 않는다. Apple의 `NSCache.totalCostLimit`은 엄격한 상한이 아니므로, 출력 이미지 캐시에 대해서는 앱이 직접 제거 시점을 결정한다. [Apple NSCache 용량 제한 설명](https://developer.apple.com/documentation/foundation/nscache/totalcostlimit?changes=_1)

| 모드 | 16 GiB Mac의 정밀 캐시 | 16 GiB Mac의 썸네일 캐시 | 작은 메모리에서의 추가 상한 |
|---|---:|---:|---|
| 최우선 | 256 MiB | 128 MiB | 각각 물리 메모리 ÷ 64, ÷ 128 |
| 쾌적, 기본값 | 128 MiB | 64 MiB | 각각 물리 메모리 ÷ 128, ÷ 256 |
| 일반 | 96 MiB | 48 MiB | 각각 물리 메모리 ÷ 160, ÷ 320 |
| 느림 | 64 MiB | 32 MiB | 각각 물리 메모리 ÷ 256, ÷ 512 |

각 캐시는 표의 MiB 값과 물리 메모리 비율 중 작은 값을 상한으로 쓴다. 기본값의 **128 + 64 = 192 MiB는 앱이 관리하는 출력 이미지 캐시 두 개의 합계**다. 앱 전체 메모리가 192 MiB 이하라는 뜻은 아니다. 화면 맞춤·확대 배율 1인 페이지의 출력 비트맵 계산 예산은 기존처럼 물리 메모리 ÷ 64, 최소 128 MiB·최대 256 MiB이며 캐시 상한과 별개다.

화면 맞춤·확대 배율 1인 페이지의 타일 상한은 `sqrt(페이지 예산 / 표시 장수 / 8)`을 256픽셀 단위로 내림하여 계산한다. 정사각형 HDR 출력의 픽셀당 8바이트를 기준으로 가장 무거운 경우를 먼저 고려한다. 해당 상태의 실제 요청은 이 상한과 화면 크기·화면 배율로 계산한 크기 중 작은 쪽이다. 픽셀 요청 자체도 256픽셀 단위로 묶어 몇 픽셀의 창 크기 변화로 재디코딩하지 않게 했다.

이 페이지 예산은 **화면 맞춤·확대 배율 1에서 새로 요청하는 현재 페이지 출력 비트맵의 계산 예산**이다. 실제 크기 보기 또는 확대 배율 1을 넘는 명시적인 확대에서는 기존의 긴 변 최대 8,192픽셀 상한을 유지하며 페이지 계산 예산보다 메모리를 더 사용할 수 있다. 프로세스 전체 메모리의 상한이나 디코더의 순간 최대 메모리 보장은 아니다. 화면 크기 변경 중 유지되는 이전 비트맵, Quick Look 미리보기, 코덱 작업 공간, 이미지 소스, GPU·레이어 자원은 별도로 존재한다. 캐시와 뷰가 동일한 `CGImage`를 참조하는 경우에는 두 개의 독립 복사본이 생기는 것도 아니다.

캐시 상한이 줄어들면 기존 출력 캐시와 디코더 소스 캐시를 정리하고 이전 세대의 완료 작업이 캐시를 다시 채우지 않도록 한다. 메모리 경고와 앱 비활성 상태에서는 두 출력 캐시 예산을 정상의 1/4로 줄이고, 심각한 메모리 압박에서는 두 캐시 예산을 0으로 바꾼다. 이 상태에서는 선읽기도 멈춘다. 이미 화면에서 필요한 결과는 표시할 수 있도록 반환한다. 압박 해소 신호가 오면 현재 상태와 선택 모드의 실행 한도·캐시 정책으로 돌아간다. 원본을 처리하는 코덱 작업 공간, GPU·화면 참조, OS Quick Look·파일 캐시는 이 두 캐시 상한에 포함되지 않는다.

## 화면 전환과 선읽기

몽땅보기·사이드바의 썸네일 요청은 Quick Look과 같은 128픽셀 버킷을 사용한다. 썸네일 크기 슬라이더가 한 픽셀 움직일 때마다 작업을 재시작하지 않는다. Quick Look 요청이 취소되었을 때 무거운 정밀 디코더로 잘못 넘어가던 가능성도 차단했다.

뷰어 타일과 썸네일은 요청 세대를 검사하여 이전 파일·이전 크기의 늦은 성공이나 실패가 현재 화면을 덮지 못하게 한다. 화면 밖으로 나가면 세대를 무효화하고 뷰의 이미지 참조를 해제한다. 뷰어의 별도 미리보기 Task도 부모 Task 취소와 연결해 정밀 렌더가 끝날 때까지 불필요한 Quick Look 요청을 유지하지 않는다.

같은 파일에서 확대하거나 창 크기를 바꿀 때는 기존 이미지를 남겨 둔다. 출력 크기가 바뀌면 60ms를 기다린 뒤 마지막 크기의 정밀 렌더를 시작한다. 새 결과가 오면 교체하므로 매번 빈 화면부터 시작하지 않는다. 다른 파일 버전으로 바뀌면 기존 결과를 지운다.

선읽기는 현재 화면의 실제 타일 크기에서 계산한, 긴 변 최대 1,024픽셀 미리보기만 사용한다. 고정 1,536픽셀 정밀 렌더 선읽기를 제거하여 현재 타일과 캐시 크기가 어긋나거나 큰 RAW/HDR 작업이 전경과 경쟁하는 일을 줄였다.

페이지 이동 후에는 현재 모드·저장장치의 대기 시간을 적용하고 다음 페이지를 우선 준비한다. 후보 목록은 표시 장수에 따라 만들지만 실제 읽는 수는 현재 상한인 0~4장이다. 기본 쾌적·내부 SSD는 350ms 후 최대 2장, 외장 SSD는 최소 600ms 후 최대 1장이며 SD·네트워크·분류 불명은 읽지 않는다. 이웃 미리보기는 하나씩 요청하고 실행 시점에도 정책을 재확인한다. 다시 페이지를 넘기거나 폴더·몽땅보기로 전환하면 이전 선읽기를 취소한다. 몽땅보기에서는 보이는 셀 자체가 미리보기를 요청하며 별도의 정밀 선읽기를 실행하지 않는다.

## 색상, HDR와 실제 크기 보기

보정 없는 일반 SDR 이미지는 ImageIO가 만든 방향 보정·축소 결과를 그대로 표시한다. 비트맵에 포함된 ICC 색공간을 유지하며 화면 색상 관리는 Core Animation에 맡긴다. 따라서 모든 일반 사진을 Core Image를 거쳐 Display P3 half float 비트맵으로 다시 만드는 비용을 줄인다.

HDR 후보는 이 빠른 경로와 구분한다. Apple HDR gain map과 macOS 15 이상의 ISO gain map을 확인하고, 필요한 경우 `.expandToHDR`와 기존 Core Image의 확장 선형 색공간·RGBA half float 경로를 유지한다. Apple은 gain map HDR을 읽는 데 `.expandToHDR` 또는 ImageIO의 `kCGImageSourceDecodeToHDR`를 사용하도록 설명한다. [Apple WWDC23 HDR 읽기](https://developer.apple.com/videos/play/wwdc2023/10181/), [Apple WWDC24 Adaptive HDR](https://developer.apple.com/videos/play/wwdc2024/10177/)

ISO gain map 키는 로컬 SDK의 `kCGImageAuxiliaryDataTypeISOGainMap`이며 macOS 15부터 사용할 수 있으므로 실행 환경 검사를 적용했다. 일반적인 높은 비트 깊이만으로 실제 HDR을 확정할 수 없으며, 선형 확장 색공간은 HDR 전송함수 검사만으로 식별되지 않을 수도 있다. 따라서 이번 변경에서 HDR 출력 전체를 파일 확장자만 보고 RGBA8로 바꾸지는 않았다.

렌더 결과에는 원본의 방향과 사용자 회전을 반영한 픽셀 크기도 보관한다. 실제 크기 보기의 화면 크기는 제한된 미리보기 비트맵 치수가 아니라 이 원본 치수와 해당 창의 화면 배율로 계산한다. 원본 치수가 아직 없는 Quick Look 미리보기는 화면 맞춤으로 먼저 보여 준다.

실제 크기 보기와 명시적인 확대에서는 화면 맞춤용의 작은 페이지 예산을 적용하지 않고 기존의 긴 변 8,192픽셀 상한을 유지한다. 메모리 절약 때문에 기존 확대 검사의 세부 해상도를 낮추지 않도록 한 선택이다. 원본이 8,192픽셀보다 크면 기존과 같이 표시 비트맵이 축소될 수 있다. 이 범위를 넘어선 세부 검사를 위해 화면에 보이는 원본 영역만 타일로 디코딩하는 기능은 후속 개선 대상이다. 원본 해상도 내보내기는 별도이며 전체 크기로 렌더하고 결과를 출력 캐시에 남기지 않는다.

파일 캐시는 표준화한 URL뿐 아니라 파일 크기와 수정 시각을 키에 포함한다. 캐시 비우기 세대도 확인하므로 비우기 전에 시작한 요청이 나중에 끝나도 지운 캐시를 다시 채우지 않는다. 파일 크기와 수정 시각을 둘 다 보존한 외부 변경까지 감지하는 콘텐츠 해시를 계산하는 방식은 아니다.

## 이전 엔진의 측정 기록과 현재 검증 범위

**이 절의 시간 표와 과거 화면 검증은 자동 자원 조절을 도입하기 전 결과다. 4개 정밀 디코더를 사용하는 이전 성능 설정의 기록을 보존한 것으로, 현재 기본 쾌적 모드 또는 현재 최우선 모드의 처리 시간을 나타내지 않는다.** 새 쾌적 모드는 Quick Look·정밀·정보 읽기를 합쳐 최대 2개로 제한하며 QoS와 저장장치 대기 정책도 달라졌다. 새 모드에서 같은 조건의 속도 비교를 완료하기 전에는 아래 시간을 새 기본값의 성능으로 인용하지 않는다.

성능 비교는 `ImageLoadingBenchmarkTests`의 선택 실행 시험으로 진행했다. 변경 전후 모두 같은 Mac의 debug 빌드에서 네이티브 이미지 처리가 가능한 동일한 실행 조건을 사용했다. 고정 난수 패턴을 넣은 6,000×4,000 JPEG 한 개의 실제 크기는 98,550,157바이트다. 이 파일에 서로 다른 경로의 하드 링크 300개를 만든다. 저장 공간 약 30 GB를 실제로 복제하지 않으며, 파일 데이터가 파일 시스템 캐시에 있는 조건이다.

각 페이지는 1,280픽셀 요청으로 10·5·4장을 렌더하고, 캐시를 비운 첫 요청과 같은 요청의 재사용 시간을 구분한다. 300개 경로 시험은 512픽셀로 20개씩 정밀 파이프라인에 요청한다. 이 시험에서 `prefersHDR`는 켜져 있지만 입력은 일반 SDR JPEG다. 따라서 SDR의 불필요한 half float 변환 제거도 비교에 반영된다.

**이는 `ImagePipeline` 정밀 렌더·썸네일 대체 경로의 측정이다. 몽땅보기의 Quick Look 표시 시간이나 앱 UI 전체 응답 시간을 직접 측정한 결과가 아니다.** 첫 요청도 운영체제의 파일 캐시를 비운 콜드 디스크 읽기를 뜻하지 않는다.

| 측정 항목 | 이전 엔진 개선 전 | 이전 엔진 개선 후, 정밀 4개 |
|---|---:|---:|
| 10장, 1,280픽셀 첫 요청 | 6.624초 | 1.730초 |
| 5장, 1,280픽셀 첫 요청 | 2.675초 | 1.052초 |
| 4장, 1,280픽셀 첫 요청 | 2.777초 | 0.631초 |
| 300개 경로, 512픽셀 순회 | 143.133초 | 33.508초 |
| 10장 출력 비트맵 합계 | 87,347,200바이트, 약 83.3 MiB | 43,673,600바이트, 약 41.7 MiB |

위 개선 전 값은 `/private/tmp/imageviewer-baseline-results.txt`, 개선 후 값은 `/private/tmp/imageviewer-final-benchmark.txt`의 당시 완료된 실행에서 확인했다. 당시 개선 후 측정은 M3·24 GiB의 정밀 디코더 4개 설정이었다. 10장 출력 비트맵 바이트 수가 절반으로 줄어든 것은 일반 SDR 사진을 HDR용 half float로 다시 복사하지 않은 결과이며, 프로세스 전체 메모리가 절반으로 줄었다는 뜻은 아니다. 동일 페이지의 캐시 재사용은 양쪽 모두 1ms 미만이었다. 이 단발 측정에서 나온 미세 시간 차이를 캐시 속도의 의미 있는 우열로 해석하지 않으며, 전체 수치를 모든 사진·기기에 적용할 속도 배수로 해석하지 않는다.

별도의 `ThumbnailLoadingIntegrationTests`는 약 33 MB 비압축 TIFF 한 개에 300개 하드 링크를 만들어 실제 Quick Look 서비스를 검사한다. 빠른 취소 100건 이후 복구, 중복 요청 공유, 20개·300개 미리보기와 10장 요청의 완료를 확인한다. 같은 물리 파일과 시스템 캐시의 영향을 받으므로 출력되는 처리 시간을 실제 사진 300장의 속도나 개선 배수 주장에 사용하지 않는다.

당시 네이티브 화면 검증은 별도 테스트 앱과 약 33.2 MB TIFF 가로·세로 10종에 연결된 300개 경로로 진행했다. 10·5·4장 표시, 빠른 다음·이전 페이지 왕복, 몽땅보기 스크롤과 실제 크기·화면 맞춤 전환을 확인했다. 확대 이미지가 타일 경계를 넓히거나 파일명을 잘라내지 않도록 이미지와 타일의 레이아웃 크기를 함께 고정했고, 당시 릴리스 실행 파일에서 4장 실제 크기 보기의 경계·파일명과 화면 맞춤 복귀를 다시 확인했다.

일반 검증과 선택 실행 방법은 다음과 같다. 프로젝트 루트에서 실행하며 선택 실행 시험이 만든 임시 사진은 시험 종료 후 정리된다.

```sh
swift test --disable-sandbox

IMAGEVIEWER_BENCHMARK=1 swift test --disable-sandbox --filter ImageLoadingBenchmarkTests

IMAGEVIEWER_NATIVE_THUMBNAILS=1 swift test --disable-sandbox --filter ThumbnailLoadingIntegrationTests

IMAGEVIEWER_WORKER_TUNING=1 swift test --disable-sandbox --filter ImageLoadingBenchmarkTests/appleSiliconWorkerTuning
```

빠른 개발 확인이 필요하면 JPEG 시험에 `IMAGEVIEWER_BENCHMARK_COUNT=30`처럼 경로 수를 지정할 수 있다. 최종 300장 조건을 확인할 때는 기본값 300을 사용한다. 빌드 캐시 쓰기가 제한된 환경에서는 `CLANG_MODULE_CACHE_PATH`와 `SWIFTPM_MODULECACHE_OVERRIDE`를 쓰기 가능한 임시 폴더로 지정하고 `--scratch-path`로 별도 빌드 위치를 설정할 수 있다.

현재 모니터·저장장치 검증은 CPU 제한의 진입·회복 지연, 잘못된 표본, 카운터 순환, SD 정보 우선순위, 초기 알림과 모니터 해제를 다룬다. 이 M3·24 GiB에서 프로젝트 폴더가 있는 내부 장치만 읽은 실제 확인에서도 Foundation·Disk Arbitration·IOKit이 내부/비이동식/Solid State/Apple Fabric을 보고했고 분류 결과는 내부 SSD였다. 약 2초 구간의 독립 CPU 카운터 계산과 모니터 표본은 약 50.4%로 일치했다. 이는 감지 기능의 작동 확인이며 사진 로딩 벤치마크나 다른 앱에 미치는 영향의 측정은 아니다.

추가 확인에는 서로 다른 실제 사진 300장, JPEG·HEIC·RAW·TIFF·HDR 혼합 폴더, 실제 16 GiB Mac, 외장 SSD·SD 카드 리더·네트워크 폴더, 다른 앱을 동시에 사용하는 조건이 필요하다. SSD 속도, 코덱별 전체 해상도 작업 공간, 운영체제 미리보기 캐시, 다른 앱의 메모리 사용량 때문에 모든 조건에서 일정한 로딩 시간이나 프로세스 메모리 최대치를 보장하지 않는다. 자동 조절은 다른 앱과의 경쟁을 줄이기 위한 설계이며 다른 앱에 영향이 전혀 없다는 보장은 아니다.
